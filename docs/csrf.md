## Introduction

Cross-site request forgeries are a type of malicious exploit whereby unauthorized commands are performed on behalf of an authenticated user. reef's `middleware.PreventRequestForgery` protects the routes that authenticate with cookies from [cross-site request forgery](https://en.wikipedia.org/wiki/Cross-site_request_forgery) (CSRF) attacks.

#### An Explanation of the Vulnerability

In case you're not familiar with cross-site request forgeries, let's discuss an example of how this vulnerability can be exploited. Imagine your application has a `/user/profile-information` route that accepts a `PUT` request to change the authenticated user's email address. Most likely, this route expects an `email` input field to contain the email address the user would like to begin using.

Without CSRF protection, a malicious website could submit a request to your application's route carrying the malicious user's own email address. The browser would attach your user's session cookie, and the request would succeed on their behalf. If the malicious website sends it as soon as the page is loaded, the malicious user only needs to lure an unsuspecting user of your application to visit their website, and their email address will be changed in your application.

To prevent this vulnerability, we need to inspect every incoming `POST`, `PUT`, `PATCH`, or `DELETE` request for a secret session value that the malicious application is unable to access.

## Preventing CSRF Requests

reef generates a CSRF "token" for each [session](session.md) the application manages: `StartSession` gives every session one, 40 random characters stored in its `_token` attribute. Since the token lives in the session and changes whenever it is regenerated, a malicious application is unable to read it. You may read the current session's token yourself:

```go
token := session.FromContext(c).Token()
```

`PreventRequestForgery` lets a request through when any of these holds:

1. its method is `GET`, `HEAD` or `OPTIONS`, which must never change state;
2. its path matches one of the [excluded patterns](#excluding-uris);
3. the browser marked it `Sec-Fetch-Site: same-origin`;
4. it carries the session's token, as a `_token` input field, an [`X-CSRF-TOKEN`](#x-csrf-token) header, or an encrypted [`X-XSRF-TOKEN`](#x-xsrf-token) header.

Anything else is refused with a [`419`](#token-mismatches). Every response to a request the check lets through, error responses included, then carries a fresh `XSRF-TOKEN` cookie holding the session's token as it stands after the request, so a token regenerated by a sign-in reaches the frontend at once.

### Registering the Middleware

reef applies the middleware to nothing by itself. Build it once with the encrypter and your session's cookie settings, which the `XSRF-TOKEN` cookie copies, and put it in the middleware group of your cookie-authenticated routes:

```go
csrf := middleware.PreventRequestForgery(middleware.CsrfConfig{
	Encrypter: encrypter,
	Lifetime:  sessions.Lifetime,
	Path:      sessions.Path,
	Domain:    sessions.Domain,
	Secure:    sessions.Secure,
	SameSite:  sessions.SameSite,
	Except:    []string{"webhooks/*"},
})

webGroup := []web.Middleware{
	middleware.Cookies(encrypter, "locale"),
	session.StartSession(sessions),
	csrf,
}
```

The `CsrfConfig` fields are:

- `Encrypter` opens an echoed `X-XSRF-TOKEN` header. Use the same encrypter as the `Cookies` middleware, which seals the cookie on the way out.
- `Lifetime` is how long the `XSRF-TOKEN` cookie lasts (its `Expires` and `Max-Age`), and `Path`, `Domain`, `Secure` and `SameSite` are its attributes. Copy them from your session configuration, so the token cookie lives exactly as long and as wide as the session it belongs to.
- `Except` lists the path patterns never verified. See [excluding URIs](#excluding-uris).

> [!WARNING]
> The middleware must run inside `middleware.Cookies` and `session.StartSession`, that is, after both in the list. Without a session it refuses every request, reads included, with a `419`; without the cookie middleware outside it, the `XSRF-TOKEN` cookie leaves unencrypted and its echo can never match.

In a typical application, the `Web` group (the account routes outside `/api`) runs the check for every route, and the `/api` routes that need it add `m.CSRF` on top of the `API` group, after `m.Auth`, so a guest gets a `401` before the CSRF check could answer `419`:

```go
r.Middleware(m.Auth, m.CSRF).Group(func(r *web.Router) {
	r.Get("/favourites", c.Favourites.Index).Name("favourites.index")
	r.Post("/favourites/{airport}", c.Favourites.Store).Name("favourites.store")
})
```

### Origin Verification

Modern browsers send a `Sec-Fetch-Site` header on every request, saying whether it came from the same origin, the same site, or another site. When it says `same-origin`, the request is let through without a token: a cross-site page can't make the browser claim that.

Only `same-origin` counts. A request marked `same-site` (from a sibling subdomain) or `cross-site`, and one from a browser that sends no header at all, falls back to the token check. reef has no setting to allow same-site requests, and none to rely on the header alone.

### CSRF Tokens and SPAs

An SPA can't embed a token in a server-rendered form, so it fetches the cookie instead. Register a route in the CSRF-protected group that does nothing but answer, and the middleware attaches the `XSRF-TOKEN` cookie to its response. Keeping Sanctum's path for it makes it familiar:

```go
// CsrfCookie is an empty 204 for the XSRF-TOKEN cookie the web group's CSRF
// middleware attaches; the SPA calls it before its first state change.
func CsrfCookie(*web.Context) (*web.Response, error) {
	return web.NoContent(), nil
}
```

```go
r.Middleware(m.Web...).Group(func(r *web.Router) {
	r.Get("/sanctum/csrf-cookie", controllers.CsrfCookie).Name("sanctum.csrf-cookie")
})
```

The SPA calls it once, before its first state-changing request, then echoes the cookie on every request as described [below](#x-xsrf-token). Remember to allow the route's path in your [CORS configuration](routing.md#cross-origin-resource-sharing-cors) when the frontend is served from another origin.

### Excluding URIs

Sometimes you may wish to exclude a set of URIs from CSRF protection. For example, a payment provider's webhook will not know what CSRF token to send to your routes.

Typically, you should place these kinds of routes outside the CSRF-protected middleware group. A payment gateway's webhook, for instance, can be an `/api` route when the `API` group has no CSRF check. You may also exclude paths with `CsrfConfig.Except`:

```go
middleware.CsrfConfig{
	// ...
	Except: []string{"webhooks/*", "stripe/*"},
}
```

The patterns are matched against the request path like `c.Is`: without the leading slash, with `*` crossing slashes, so `webhooks/*` covers every path below `/webhooks/`. Full URLs are not supported; the patterns see the path alone. An excluded request still gets the `XSRF-TOKEN` cookie.

## X-CSRF-TOKEN

In addition to checking for the CSRF token as a `_token` input field (in a JSON or form body, or the query string), the middleware checks for the token in the `X-CSRF-TOKEN` request header. This header carries the plain token, so you might render it into a page you serve:

```html
<meta name="csrf-token" content="...">
```

Then send it with every request:

```js
fetch('/user/profile-information', {
  method: 'PUT',
  headers: {
    'Content-Type': 'application/json',
    'X-CSRF-TOKEN': document.querySelector('meta[name="csrf-token"]').content,
  },
  body: JSON.stringify({ name, email }),
});
```

The middleware reads one source only: the `_token` input when it isn't empty (read like `c.String("_token")`), else the `X-CSRF-TOKEN` header when it isn't empty, else `X-XSRF-TOKEN`. A wrong token in an earlier source is never rescued by a right one in a later source. Tokens are compared in constant time, and an empty session token never matches.

## X-XSRF-TOKEN

reef stores the current CSRF token in an encrypted `XSRF-TOKEN` cookie, attached to every response the middleware lets through. The middleware's `XSRFCookie` constant holds the name. The cookie is deliberately not `HttpOnly`, so your JavaScript can read it and send its value back in the `X-XSRF-TOKEN` header.

Some JavaScript libraries, like Axios and Angular, do this automatically on same-origin requests. Without one, read the cookie and set the header yourself:

```js
function getXsrfToken() {
  const match = document.cookie.match(/XSRF-TOKEN=([^;]+)/);
  return match ? decodeURIComponent(match[1]) : '';
}

await fetch('/login', {
  method: 'POST',
  headers: {
    'Content-Type': 'application/json',
    Accept: 'application/json',
    'X-XSRF-TOKEN': getXsrfToken(),
  },
  body: JSON.stringify({ email, password }),
});
```

Send the cookie's value URL-decoded, as above. The middleware decrypts the header as the `XSRF-TOKEN` cookie, so a value sealed for any other cookie's name (the session cookie replayed as a token, say) is refused, as is one sealed under a key the encrypter doesn't hold.

## Token Mismatches

A request that fails the check gets a `419` (Laravel's "Page Expired", a status `net/http` has no name for), and its controller never runs:

```json
{"message": "CSRF token mismatch."}
```

The usual cause is a stale token: the session expired, or the user signed in on another tab and the token was regenerated. A frontend can recover by fetching the CSRF cookie again and retrying the request once. You may return the same error from your own middleware with `middleware.TokenMismatch()`.

## Testing

reef never switches CSRF protection off in tests, so a test exercising a protected route has to send the token, just as the browser does. A test client built on `testkit` can do what the SPA does: fetch `/sanctum/csrf-cookie` and echo the cookie as `X-XSRF-TOKEN` on every state-changing request, with an option to leave it off to prove the `419`. See [HTTP tests](http-tests.md).

## Available Functions

#### `middleware.PreventRequestForgery`

`PreventRequestForgery(middleware.CsrfConfig{...})` is the CSRF check, run inside `Cookies` and `StartSession`.

#### `middleware.CsrfConfig`

The `XSRF-TOKEN` cookie's settings (`Lifetime`, `Path`, `Domain`, `Secure`, `SameSite`), the `Encrypter` an echoed header is opened with, and the `Except` path patterns.

#### `middleware.XSRFCookie`

The constant `"XSRF-TOKEN"`: the readable token cookie's name.

#### `middleware.TokenMismatch`

`TokenMismatch()` is the `419` `CSRF token mismatch.` error.
