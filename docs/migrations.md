## Introduction

Migrations are like version control for your database, allowing your team to define and share the application's schema. reef's migrations are plain SQL files, run by [goose](https://github.com/pressly/goose): each file is numbered, applied in order inside its own transaction, and recorded in goose's version table, `goose_db_version`. The files are embedded in your binary, so a release migrates its database without the source tree.

reef has no schema builder. Where a Laravel migration calls `Schema::create`, a reef migration writes the `CREATE TABLE` itself: Postgres's own DDL is the most precise way to say what you want, and the SQL you review is the SQL that runs.

The `github.com/atobeach/reef/migration` package provides the console commands (`migrate`, `migrate:status`, `migrate:rollback` and `make:migration`) and the `Migrator` they run on.

## Generating Migrations

You may use the `make:migration` command to generate a new migration. Its name says what the migration does, in snake case:

```shell
flights make:migration add_votes_to_users_table
```

The new file is placed in your migrations directory (conventionally `database/migrations`), numbered one past the newest migration there, with five digits, and the command prints its path:

```shell
Migration [database/migrations/00007_add_votes_to_users_table.sql] created successfully.
```

Run the command from your module root, since the directory is relative to the working directory; when the directory isn't there, the command says so rather than creating it.

The name must start with a lower-case letter and contain only lower-case letters, digits and underscores, and it must not repeat the name of an existing migration. The file starts from this stub:

```sql
-- Why this change (the column, the index, the query it serves).

-- +goose Up


-- +goose Down

```

## Migration Structure

A migration file has two sections. Statements under `-- +goose Up` apply the change; statements under `-- +goose Down` reverse it. Start the file with a comment saying why the change is made: the column, the index, the query it serves.

```sql
-- The seat each passenger on a booking has chosen. A passenger has at most
-- one seat, and a seat number is taken once per flight.

-- +goose Up
CREATE TABLE public.seats (
    id bigint GENERATED BY DEFAULT AS IDENTITY NOT NULL,
    passenger_id bigint NOT NULL,
    flight_id bigint NOT NULL,
    number character varying(4) NOT NULL,
    created_at timestamp(0) without time zone DEFAULT CURRENT_TIMESTAMP NOT NULL,
    CONSTRAINT seats_pkey PRIMARY KEY (id),
    CONSTRAINT seats_passenger_id_unique UNIQUE (passenger_id),
    CONSTRAINT seats_flight_id_number_unique UNIQUE (flight_id, number),
    CONSTRAINT seats_passenger_id_foreign FOREIGN KEY (passenger_id) REFERENCES public.passengers(id) ON DELETE CASCADE,
    CONSTRAINT seats_flight_id_foreign FOREIGN KEY (flight_id) REFERENCES public.flights(id) ON DELETE CASCADE
);

-- +goose Down
DROP TABLE public.seats;
```

A migration may change data as well as schema. When there is nothing to reverse, say so in the down section, which still needs a statement:

```sql
-- +goose Up
UPDATE public.users
SET two_factor_secret = NULL
WHERE provider IS NOT NULL AND password IS NULL;

-- +goose Down
-- The cleared secrets are gone; nothing to restore.
SELECT 1;
```

The file's annotations are goose's. A statement that itself contains semicolons, such as a function body, goes between `-- +goose StatementBegin` and `-- +goose StatementEnd`.

### Migrations Without a Transaction

Each migration runs in its own transaction, so a failing statement leaves nothing half-applied. Some statements, such as `CREATE INDEX CONCURRENTLY`, can't run inside a transaction; put `-- +goose NO TRANSACTION` above the up section of such a migration:

```sql
-- Speeds up the sweep that releases lapsed holds, which scans unpaid bookings
-- by hold expiry.

-- +goose NO TRANSACTION

-- +goose Up
CREATE INDEX CONCURRENTLY bookings_hold_expires_at_index ON public.bookings (hold_expires_at) WHERE paid_at IS NULL;

-- +goose Down
DROP INDEX CONCURRENTLY bookings_hold_expires_at_index;
```

### Embedding Migrations

Your migrations package embeds the files, so the binary carries them:

```go
// Package migrations holds the schema migrations, embedded so the binary
// migrates a database without the source tree.
package migrations

import "embed"

// FS is every migration, NNNNN_name.sql in version order.
//
//go:embed *.sql
var FS embed.FS
```

Only the `.sql` files at the root of the file system are migrations. Each must be named `NNNNN_name.sql` with a version of 1 or more, and no two may share a version; the commands refuse to run otherwise.

## Running Migrations

To run all of your outstanding migrations, run the `migrate` command:

```shell
flights migrate
```

Each pending migration runs in version order, and the command prints its name, its duration and `DONE`:

```shell
  00007_add_votes_to_users_table ... 4.21ms DONE
```

With nothing pending, it prints `Nothing to migrate.`. If a migration fails, the run stops there: the migrations before it stay applied, the failed one leaves nothing behind (its transaction rolls back, unless it runs [without one](#migrations-without-a-transaction)), and the command exits with an error naming the failed version, such as `migration: partial migration error (type:sql,version:7): ...`. An `After` hook can then run River's queue migrations too, so one command prepares the whole database (see [registering the migration commands](#registering-the-migration-commands)).

The command accepts `--force` so deploy scripts can pass it, but it never prompts, in production or anywhere else.

### Checking Migration Status

The `migrate:status` command lists every migration and whether it has run:

```shell
flights migrate:status

  00001_baseline ............................................ Ran
  00002_add_cabin_class_to_fare_quotes_table ................ Ran
  00003_create_seats_table .................................. Ran
  00004_add_delayed_until_to_flights_table .................. Ran
  00005_add_hold_expires_at_to_bookings_table ............... Ran
  00006_clear_two_factor_on_google_only_users ............... Ran
  00007_add_votes_to_users_table ............................ Pending
```

It only reads: on a database that has never been migrated (no `goose_db_version` table yet), every migration is pending.

### Rolling Back Migrations

To roll back the latest migration, use the `migrate:rollback` command. The `--step` option rolls back that many migrations, newest first:

```shell
flights migrate:rollback

flights migrate:rollback --step=3
```

`--step` must be at least 1. With nothing applied, the command prints `Nothing to rollback.`.

> [!WARNING]
> The first migration is the schema baseline, and its down section would drop every table. A rollback that would include it is refused as a whole (`the schema baseline cannot be rolled back`), and nothing is rolled back.

### Running Migrations in Production

Several servers may run `migrate` at once, such as every instance of a deploy starting together. goose takes a Postgres session-level advisory lock before it migrates, so the others wait (retrying every 5 seconds, for up to 5 minutes, before failing) and each migration runs exactly once.

> [!WARNING]
> A session-level lock (and some DDL) needs a real database session. If your app connects through a transaction pooler, such as PgBouncer in transaction mode, migrate over a direct connection to the server. A `DB_DIRECT_PORT` setting that the migration commands' `Pool` func prefers is one way to do that.

## After a Migration

A migration that changes a table a model is generated from must be followed by regenerating the models:

```shell
go generate ./app/models
```

See [generating models](models.md#generating-models). You don't need to rebuild the test databases yourself: they are rebuilt from the migrations whenever a migration file changes, which `migration.Fingerprint` detects (see [database testing](database-testing.md)).

## Registering the Migration Commands

The `migration.Commands` struct configures the four commands, and its `All` method returns them for your [console kernel](console.md). Register them like this:

```go
k.Register(migration.Commands{
	FS:    migrations.FS,
	Dir:   filepath.Join("database", "migrations"),
	Pool:  migrationPool,
	Adopt: migrations.LaravelHandover,
	After: func(c *console.Context, pool *pgxpool.Pool) error {
		versions, err := queue.Migrate(c, pool)
		for _, version := range versions {
			c.Linef("  River migration %03d ... DONE", version)
		}

		return err
	},
}.All()...)
```

| Field | Meaning |
|-------|---------|
| `FS` | The migrations, usually your embedded `migrations.FS`. |
| `Dir` | Where `make:migration` writes, relative to the working directory (the module root). |
| `Pool` | `func(c *console.Context) (*pgxpool.Pool, func(), error)`: opens the database to migrate and returns a func that releases it. It should be a direct session (see [running migrations in production](#running-migrations-in-production)). |
| `Adopt` | Optional: records, before `migrate` runs anything, the migrations a database migrated by an earlier tool already holds (see [adopting an existing database](#adopting-an-existing-database)). |
| `After` | Optional: runs once the app's migrations are up, on every `migrate` (even when there was nothing to migrate), so one command prepares the whole database. |

A `Pool` func that opens a direct connection with [`db.Open`](database.md#configuration) and closes it afterwards looks like this:

```go
func migrationPool(c *console.Context) (*pgxpool.Pool, func(), error) {
	pool, err := db.Open(c, directURL)
	if err != nil {
		return nil, nil, err
	}

	return pool, pool.Close, nil
}
```

## Adopting an Existing Database

If you're moving an existing application to reef, its production database was migrated by another tool, and its schema already holds what your first migrations create. Running them would fail on "already exists". An adopt step tells `migrate` which pending migrations to record as applied, without running them.

An adopt func receives the pending migrations, in version order, and returns the ones the database already holds:

```go
Adopt: func(c *console.Context, tx *sql.Tx, pending []migration.Migration) ([]migration.Migration, error) {
	// Inspect the database through tx and pick the migrations it already holds.
},
```

It must return a leading run of `pending` (the first few, in order), so goose's history stays gapless; picking a migration out of order fails the whole step. It runs inside the adopt step's transaction, so it may read the database through `tx`, but it must not change the schema. The transaction holds goose's advisory lock, so two servers can't interleave with each other or with goose; an error leaves the database untouched. If the version table doesn't exist yet, it is created exactly as goose would create it.

Each adopted migration prints `RECORDED (its schema is already there)`, and then any migrations still pending run as usual.

For example, if you're moving an existing Laravel application to reef, you might write a `LaravelHandover` adopt func in your migrations package: each migration lists the Laravel migrations it reproduces in `-- laravel: <name>` comment lines before `-- +goose Up`, and a migration is recorded when Laravel's own `migrations` table lists all of them. See [compatibility](compatibility.md) for the rest of what reef reads from a Laravel application.

## Running Migrations From Code

The commands run on a `migration.Migrator`, which you may also use directly; reef's [test kit](database-testing.md) builds each test database this way:

```go
m, err := migration.New(pool, migrations.FS)
if err != nil {
	return err
}
defer m.Close()

results, err := m.Up(ctx)
if err != nil {
	return err
}

for _, result := range results {
	fmt.Println(result.Source.Path, result.Duration)
}
```

`migration.New` never closes the pool you give it: `Close` releases only the migrator's own `database/sql` handle over it.

## Available Methods

#### `migration.New`

`New(pool *pgxpool.Pool, fsys fs.FS) (*migration.Migrator, error)` builds a migrator over the pool and the migrations in `fsys`. The pool must be a real session (not a transaction pooler), because goose's advisory lock is session-scoped.

#### `Migrator.Up`

`Up(ctx context.Context) ([]*goose.MigrationResult, error)` runs every pending migration in order, each in its own transaction unless the file says `-- +goose NO TRANSACTION`.

#### `Migrator.Status`

`Status(ctx context.Context) ([]migration.Status, error)` reports every migration, applied or pending, reading only.

#### `Migrator.Rollback`

`Rollback(ctx context.Context, steps int) ([]*goose.MigrationResult, error)` rolls back the last `steps` applied migrations, newest first. `steps` must be at least 1; a rollback that includes the first migration fails with `migration.ErrBaseline`.

#### `Migrator.Adopt`

`Adopt(ctx context.Context, adopt migration.AdoptFunc) ([]migration.Migration, error)` records as applied, without running them, the pending migrations `adopt` picks, and returns them.

#### `Migrator.Close`

`Close() error` releases the migrator's `database/sql` handle (not the pool).

#### `migration.AdoptFunc`

`func(ctx context.Context, tx *sql.Tx, pending []migration.Migration) ([]migration.Migration, error)`: picks a leading run of `pending` whose schema the database already holds.

#### `migration.Commands`

The commands' configuration (`Pool`, `FS`, `Dir`, `Adopt`, `After`); see [registering the migration commands](#registering-the-migration-commands). Its `Adopt` field has `AdoptFunc`'s shape, with the command's `*console.Context` in place of the context: `func(c *console.Context, tx *sql.Tx, pending []migration.Migration) ([]migration.Migration, error)`.

#### `Commands.All`

`All() []console.Command` returns `migrate`, `migrate:status`, `migrate:rollback` and `make:migration`.

#### `migration.Migration`

One migration file: `Version` (`int64`) and `Name`, the file name without its extension (`"00002_add_cabin_class_to_fare_quotes_table"`).

#### `migration.Status`

One migration's state on a database: the embedded `Migration` and `Applied`.

#### `migration.Parse`

`Parse(fsys fs.FS) ([]migration.Migration, error)` reads the `NNNNN_name.sql` files at the root of `fsys`, sorted by version, refusing a malformed name or a repeated version.

#### `migration.Create`

`Create(dir string, name string) (string, error)` writes `dir/NNNNN_name.sql` from the stub, numbered one past the newest migration, and returns its path: `make:migration`'s work.

#### `migration.Fingerprint`

`Fingerprint(fsys fs.FS) (string, error)` hashes every migration file's name and contents, so a test database can be rebuilt exactly when a migration changes.

#### `migration.VersionTable`

The constant `"goose_db_version"`: goose's bookkeeping table.

#### `migration.ErrBaseline`

The error a rollback that would include the first migration wraps: `the schema baseline cannot be rolled back`.
